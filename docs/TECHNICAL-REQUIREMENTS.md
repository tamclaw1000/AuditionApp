# TECHNICAL-REQUIREMENTS.md

Technical requirements for **AuditionApp**.

> Scope of this document: **how** the system is built and operated.
> Functional "what" lives in `APPLICATION-REQUIREMENTS.md`; data model and workflows live in
> `ARCHITECTURE.md`. Live decision status for every open point is tracked in `PROGRESS.md`.
>
> A cross-cutting constraint applies to **every** choice below: **low infrastructure budget**.
> Each tool must have a credible free or very-low-cost tier.

---

## 1. Architecture summary
- **Web/back office:** Oracle Apex application on Oracle Cloud Free Tier.
- **API layer:** Oracle REST Data Services (ORDS) exposes REST endpoints consumed by the
  recording apps and agents.
- **Recording apps:** native-feeling cross-platform clients (iOS / Android / macOS / Windows)
  that record, sign, and submit recordings, and call ORDS for metadata.
- **Database:** Oracle Database; business logic and validation centralized in PL/SQL so all
  clients stay behaviorally consistent.
- **Storage:** recordings live on-device for the POC; a cloud object store is planned for later.

---

## 2. Platform & development stack
1. **Web application:** Oracle Apex **26.1** (newest supported) on Oracle Cloud Free Tier,
   authored in **APEXlang** so apps export as git-diffable `.apx` text and AI agents can contribute.
2. **REST layer:** ORDS. Endpoint inventory and request/response contracts are designed **later**
   (PROGRESS item 18), after functional requirements are finalized.
3. **Recording-app framework:** cross-platform, **selection under research** (PROGRESS item 6).
   Candidates: Flutter, React Native, Expo. Must work well with ORDS REST and the low budget.
4. **Database / business logic:** Oracle Database + PL/SQL; validation and workflow rules live
   server-side.

> Note: choosing Apex for the web app must **not** bias other choices (notably storage).

---

## 3. Authentication & authorization
1. **Strategy:** OAuth2 via ORDS, covering both the Apex web session and token-based API access
   for the recording apps.
2. **Applicant:** passwordless — email login + emailed one-time code (OTP); identical on web and
   recording apps.
3. **Camp Manager:** email or username + password, optional second factor.
4. **Admin:** username + password + **mandatory** second factor every sign-in.
5. **No unverified accounts** — email verification gates account use.
6. **Recording devices** authenticate to ORDS and call the API to supply recording metadata.

---

## 4. Multi-tenancy & data isolation (critical)
Strict isolation between camps is a **top-priority** requirement, enforced with **row-level
security** in the Oracle database so a Camp Manager can never read another camp's data, and
applicants can never read other applicants' data.

---

## 5. Tamper-proof recording mechanism
1. **Record-in-app only** — no import of externally produced video files.
2. **Cryptographic signing/hashing at capture time** plus a tamper-evident watermark; any later
   modification is detectable by verifying the signature.
3. **Server-side trusted timestamping** of each recording.
4. **Liveness checks** where they do not add disproportionate complexity.
5. A recording downloaded for personal use or manual camp submission **retains** its watermark
   and signature.

---

## 6. Storage
1. **POC:** ships **without** cloud storage. Signed recordings remain **on the device** for the
   applicant to upload manually to the camp; only **lightweight recording metadata** is sent to
   the Apex DB via ORDS (small calls vs. 0.5 GB+ video files).
2. **Architecture must plan for** cloud object storage as a later addition. Selection is **under
   research** (PROGRESS item 7); candidates include Oracle Object Storage, Cloudflare R2,
   Backblaze B2 — evaluated on budget, **not** biased by the Apex choice.
3. **Virus/AV:** recordings are generated by our own app and should be virus-free by construction;
   an out-of-the-box AV-scanning service may still be added as a safeguard when cloud storage is
   introduced. Upload pipeline design is deferred (PROGRESS item 19).

## 8. Source control & branching strategy
- **`main`** = production code, **protected**; changes only via reviewed + approved PR.
- **`dev`** = completed development, **protected**; changes only via reviewed + approved PR.
- **Feature branches** = unprotected; agents/developers work here, then open a PR into `dev`.
- **Release flow:** features merge into `dev` → deploy **UAT** from `dev` → when prod-ready,
  deploy from `dev` to **Prod**, then open a `dev`→`main` PR, merge it, and tag the release on
  `main`.
- **Hotfix flow:** urgent prod bugs are fixed on a bug branch from `main` → PR **directly to
  `main`** → later a `main`→`dev` PR reflects the fix back into `dev`.

*(Active requirements-prep work currently lives on the shared `reqirements-prep` branch.)*

## 11. Logging, observability & audit
1. **Logging (Oracle/PLSQL):** use **OraOpenSource Logger**
   (https://github.com/OraOpenSource/Logger).
2. **Logging (recording apps):** approach selected per chosen platform; logs are pushed to the
   Apex app (likely via the ORDS API) since recording actions happen on the applicant's device.
3. **Observability:** a scheduled job scans Logger for exceptions over a period and reports them
   to **Telegram for Admins**.
4. **Audit (Oracle):** every meaningful table is audited on each change, recording per-column
   change history into a designated audit table (a trigger generator is available).
5. **Audit (recording apps):** completion of each recording version and each best-version
   selection is audited locally and sent to the Apex app.

## 16. Non-functional requirements
1. **Recording UX / performance:** recording must run flawlessly on every device with no slowness
   or overload; the experience should be essentially identical to the native device camera app.
2. **Scalability:** infrastructure must scale up and down easily (mostly a cloud concern; less
   critical for the POC).
3. **Internationalization:** English for the POC; structure supports French, German, Italian
   later via Apex native i18n.
4. **Privacy:** collect the minimum personal data (email only → email + first/last name max);
   US-only jurisdiction for the POC.
5. **Data retention:** configurable, default **3 years**, with **separate** policies for video
   files vs. audition metadata (the data model must support both); a **scheduled job** deletes
   anything past its retention.
